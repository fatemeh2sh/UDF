معماری هدف: Vertical Slice Clean + UDF MVVM

سند کامل معماری هدف — Vertical Slice Clean + UDF MVVM با Core Infrastructure مشترک، مرز internal، قواعد Konsist، آماده برای رشد به میلیون کاربر.

Android Kotlin Compose Hilt Multi-module Clean Arch

این سند صرفاً مستندسازی معماری هدف است؛ هیچ تغییری روی کد فعلی اعمال نمی‌شود.

۱. خلاصه‌ی اجرایی

  • الگوی معماری: Vertical Slice Clean Architecture
  • State Management: UDF MVVM (یک UiState immutable + StateFlow + SharedFlow<UiEffect>)
  • Modularization: هر feature یک ماژول مستقل با Clean کامل داخلی
  • Boundary: کلیدواژه‌ی internal + قواعد Konsist (کامپایل‌تایم گارد)
  • Cross-cutting: زیرساخت‌های متقاطع (network/database/datastore/...) فقط در :core:*
  • Inter-feature Communication: فقط از طریق FeatureEntry در :core:navigation
  • API Error Handling: گلوگاه واحد safeApiCall در :core:network — هیچ Repository نباید مستقیماً Exception شبکه را مدیریت کند
  • Testing (فاز ۱): فقط Konsist برای گارد معماری در CI؛ سایر لایه‌های تست در فازهای بعد
  • Room (محدود): پایلوت کامل فقط در :feature:calls (تماس‌های اخیر) به‌عنوان الگوی مرجع. سایر featureها فعلاً Room ندارند و مستقیم از Api می‌خوانند؛ هر feature آینده که نیاز پیدا کند، از همین الگو کپی می‌کند
  • هدف: مقیاس میلیون کاربر، استقلال تیمی، Build سریع، Crash-free ≥ ۹۹.۵٪

قاعده‌های لایه

  • UI فقط UiState می‌خواند و onXxx() صدا می‌زند.
  • ViewModel فقط UseCase تزریق می‌کند، نه Repository.
  • UseCase فقط Repository Interface می‌بیند.
  • RepositoryImpl از Api، Dao و (در صورت نیاز) DataStore استفاده می‌کند و نگاشت Dto ↔ DomainModel انجام می‌دهد.

نقش DataStore در این لایه‌بندی

  • زیرساخت کناری — در پایپ اصلی شبکه/cache نیست؛ خط‌چین نشان می‌دهد که فقط در صورت نیاز استفاده می‌شود.
  • مصرف‌کننده‌های اصلی:
    • AuthInterceptor در :core:network برای خواندن Token (مسیر خط‌چین مستقیم)
    • RepositoryImpl ها برای خواندن/نوشتن Settings، Theme، Feature Flags محلی، Last-sync timestamp
    • SessionRepository، ThemeRepository، ListUpdateStorage
  • چه چیزی در DataStore برود: فقط داده‌های کوچک key-value (Token، Boolean flag، String, Int، Long).
  • چه چیزی نرود: لیست‌های حجیم، داده‌های Pagination، روابط جدولی → اینها در Room (در صورت نیاز) قرار می‌گیرند.

۵. State Management: UDF MVVM

۵.۱ قواعد سفت

  1. یک data class UiState به ازای هر صفحه — immutable.
  2. یک StateFlow<UiState> — هرگز چند StateFlow/LiveData موازی برای فیلدهای جدا.
  3. SharedFlow<UiEffect> برای رویدادهای یک‌بار‌مصرف (Navigate, Snackbar, Toast).
  4. توابع onXxx() در ViewModel به جای sealed Action (مگر صفحه پیچیده باشد).
  5. copy() روی UiState برای هر تغییر state.
  6. در Compose: collectAsStateWithLifecycle() فقط روی همان uiState.

۵.۲ ساختار استاندارد UiState

  • یک data class با فیلدهای: data: T?, isLoading: Boolean, error: AppError? (یا sealed class ScreenState).
  • یک data class جدا برای فرم‌ها و input fields در صورت نیاز.
  • هرگز کلاس‌های Domain را مستقیم در UiState قرار نده — اگر لازم شد wrapper بزن.

۵.۳ ساختار UiEffect

  • sealed interface XxxUiEffect
  • مثال: NavigateToDetail(id), ShowSnackbar(msg), RequestPermission.

۵.۴ مزایا نسبت به وضعیت فعلی

  • حذف کامل LiveDataها.
  • حذف State پراکنده در فیلدهای جدا.
  • SSOT برای هر صفحه.
  • Recompose بهینه‌تر در Compose.
  • Test ساده (UiState فقط data است).

  • اضافه کردن Header جدید = یک تغییر در core:network.

۷. مدیریت متمرکز خطای API — safeApiCall

۷.۱ هدف

  • یک گلوگاه واحد برای همه‌ی فراخوانی‌های شبکه.
  • بررسی متمرکز Response.isSuccessful، code()، body() و errorBody().
  • تبدیل خودکار Response<T> و Exceptionها به Result<T, AppError>.
  • جلوگیری از تکرار try/catch در Repositoryها.
  • ارسال خودکار Crashlytics non-fatal برای خطاهای بحرانی.
  • آماده برای افزودن Retry/Backoff/Telemetry بدون تغییر در Repositoryها.

۷.۲ محل قرارگیری

  • :core:network → SafeApiCall.kt, ApiErrorParser.kt, ProblemDetailsDto.kt, ApiResultExtensions.kt.
  • :shared-kernel → استفاده از Result<T> و AppError موجود (همان domain/core/Result.kt و NetworkErrorMapper.kt فعلی، که به shared-kernel منتقل می‌شوند).

۷.۳ جریان داخلی

flowchart TD
    Repo["RepositoryImpl.getData()"] -->|"safeApiCall { api.xxx() }"| Safe[safeApiCall]
    Safe --> Try{"اجرای block در IoDispatcher"}

    Try -->|"Response.isSuccessful + body!=null"| OkPath["Result.Ok(body)"]
    Try -->|"Response.isSuccessful + body==null"| EmptyPath["Result.Err(AppError.Validation 'empty body')"]
    Try -->|"!isSuccessful"| Parse["ApiErrorParser.parse(errorBody)"]
    Parse --> MapHttp["NetworkErrorMapper.mapHttpCode(code, msg)"]
    MapHttp --> ErrResult["Result.Err(AppError.*)"]

    Try -->|"HttpException"| Parse
    Try -->|"IOException / Timeout / DNS / SSL"| MapNet["NetworkErrorMapper.mapException(t)"]
    MapNet --> ErrResult

    Try -->|"SerializationException"| Validation["Result.Err(AppError.Validation 'parse error')"]
    Try -->|"CancellationException"| Rethrow["throw"]
    Try -->|"Throwable"| UnknownPath["Result.Err(AppError.Unknown(t))"]

    OkPath --> Done[بازگشت به Repository]
    ErrResult --> Done
    UnknownPath --> Done
    Validation --> Done
    EmptyPath --> Done

    ErrResult -.->|"non-fatal"| Crash[Crashlytics]
    UnknownPath -.->|"non-fatal"| Crash

۷.۴ امضاهای پیشنهادی

امضاکاربرد
suspend fun <T> safeApiCall(tag: String? = null, block: suspend () -> Response<T>): Result<T>وقتی Api مستقیماً Response<T> برمی‌گرداند
suspend fun <T> safeApiCall(tag: String? = null, block: suspend () -> T): Result<T>وقتی Api فقط T برمی‌گرداند (Retrofit suspend) — با try/catch روی HttpException
suspend fun <T, R> safeEnvelopeCall(tag: String? = null, block: suspend () -> Response<EnvelopeDto<T>>, map: (T) -> R): Result<R>وقتی پاسخ سرور Envelope دارد (مثل OtpMetaEnvelopeDto) و باید unwrap + map شود

نکات:

  • Dispatcher: درون safeApiCall با withContext(IoDispatcher) تا فراخواننده مجبور به مراقبت نباشد.
  • پارامتر tag برای Logging و Tracing.
  • CancellationException هرگز catch نشود — همیشه propagate شود.

۷.۶ ApiErrorParser و ProblemDetailsDto

  • یک ProblemDetailsDto استاندارد (RFC 7807-style) در :core:network:
    • فیلدها: title, detail, code, status, errors: Map<String, List<String>>?.
  • یک ApiErrorParser که:
    1. تلاش می‌کند errorBody.string() را به ProblemDetailsDto parse کند.
    2. اگر شکست خورد، fallback به errorBody.string() خام به‌عنوان message.
    3. اگر body تهی بود، از Response.message() استفاده کند.
    4. ساختار یکپارچه برای همه‌ی endpointها فراهم می‌کند.

۷.۷ Extensions کاربردی

در :core:network:

  • Response<T>.parseErrorOrNull(json: Json): ProblemDetailsDto? — کمک به safeApiCall.
  • Result<T>.onErrorReport() — Crashlytics non-fatal خودکار.
  • Result<T>.mapData(transform: (T) -> R): Result<R> — برای نگاشت Dto → DomainModel.

flowchart LR

    RI -.->|"impl"| RImpl[RepositoryImpl]

  • UseCase همان Result را propagate می‌کند (یا با mapData نگاشت می‌کند).
  • ViewModel بسته به Result.Ok یا Result.Err، UiState را با copy() به‌روز می‌کند یا UiEffect می‌فرستد.

۷.۹ مزایا

  • صفر تکرار try/catch در Repositoryها.
  • یک نقطه برای تغییر سیاست خطا (تغییر در یک فایل = اعمال در کل پروژه).
  • Crashlytics non-fatal خودکار → دیدن خطاهای واقعی production بدون کد اضافه.
  • پایه‌ی Retry/Backoff قابل افزودن در همان safeApiCall بدون لمس Repositoryها.
  • تست‌پذیری بالا — رفتار خطا در یک جا تست می‌شود.
  • ساختار یکنواخت پیام‌های خطا برای کل اپ.

۷.۱۰ سیاست‌های قابل افزودن (آینده، بدون تغییر در Repositoryها)

  • Retry با Exponential Backoff برای کدهای 502/503/504.
  • Circuit Breaker برای endpoint های بحرانی.
  • Idempotency Key برای POSTهای حساس (Auth, Payment).
  • Telemetry: زمان پاسخ + status code → Firebase Performance Trace.
  • Rate-limit aware: احترام به Retry-After در 429.
  • Offline detection: قبل از فراخوانی، بررسی ConnectivityManager.

۷.۱۲ نسبت با وضعیت فعلی پروژه

  • در domain/src/main/kotlin/com/bt/barex/domain/core/NetworkErrorMapper.kt منطق نگاشت کد HTTP و Exception به AppError آماده است → فقط safeApiCall نازک روی آن نوشته می‌شود.
  • در data/src/main/java/com/bt/barex/data/repository/auth/AuthRepositoryImpl.kt (۴۵۹ خط) try/catch و errorBody parsing به‌صورت دستی تکرار شده‌اند → بعد از معرفی safeApiCall این تکرارها حذف می‌شوند.
  • Result و AppError موجود در domain/core/Result.kt بدون تغییر استفاده می‌شوند (فقط محل به :shared-kernel منتقل می‌شود).

۸. Room — پایلوت فقط در :feature:calls (الگوی مرجع)

محدوده‌ی کاملاً مشخص: فقط feature تماس‌های اخیر (:feature:calls) از Room استفاده می‌کند. هدف: داشتن یک پیاده‌سازی مرجع کامل که هر feature آینده‌ای که نیاز به cache/offline داشت، از روی آن کپی کند. سایر featureها (myloads، account، home، ...) بدون Room هستند و مستقیم از Api می‌خوانند.

۸.۱ چرا فقط :feature:calls؟

  • حجم دیتای مناسب: تماس‌ها رکوردهای کوچک، تعداد محدود، مرتبط با راننده.
  • ارزش آفلاین واقعی: راننده در جاده باید سابقه‌ی تماس‌هایش را حتی بدون اینترنت ببیند.
  • مدل ساده: بدون رابطه‌ی پیچیده‌ی بین جداول → الگوی تمیز.
  • Pagination از سرور: تست‌کننده‌ی الگوی کامل RemoteMediator (مهم‌ترین قسمت).
  • ریسک پایین: اگر مشکلی پیش آمد، فقط یک feature متاثر می‌شود.

calls_meta (اختیاری)timestamp آخرین refresh برای TTL

DAOها در ماژول feature تعریف می‌شوند ولی Entityها در :core:database ثبت می‌شوند تا یک Database واحد داشته باشیم.

۸.۵ مسئولیت‌های CallsRemoteMediator

LoadTypeرفتار
REFRESHپاک کردن calls + calls_remote_keys → گرفتن صفحه‌ی ۱ → upsert
APPENDخواندن nextKey آخرین آیتم → فراخوانی Api → upsert + ذخیره‌ی RemoteKey جدید
PREPENDمعمولاً endOfPaginationReached = true

نکات:

  • استفاده از safeApiCall برای فراخوانی شبکه.
  • RoomDatabase.withTransaction { ... } برای atomic insert.
  • TTL: مثلاً ۱۵ دقیقه — اگر cachedAt expired شد در REFRESH تازه می‌شود.

۸.۶ جریان کامل از UI تا Room

flowchart TD
    UI[CallsScreen] -->|"collectAsLazyPagingItems"| VM[CallsViewModel]
    VM -->|"pagedCalls: Flow PagingData Call"| UC[GetPagedCallsUseCase]
    UC --> Repo[CallsRepository]
    Repo -.->|"impl"| RImpl[CallsRepositoryImpl]
    RImpl --> Pager[Pager]
    Pager -->|"PagingSource"| Dao[CallsDao]
    Pager -->|"RemoteMediator"| RM[CallsRemoteMediator]
    RM --> SafeCall[safeApiCall]
    SafeCall --> Api[CallsApi]
    RM --> DB[(Room calls + calls_remote_keys)]
    Dao --> DB
    Dao -->|"PagingData"| Pager

۸.۷ قواعد طلایی الگو

  1. UI هرگز مستقیم Api نمی‌خواند — همیشه از Room.
  2. ViewModel فقط Flow<PagingData<Call>> می‌بیند — جزئیات Room/شبکه پنهان.
  3. Mapping در دو لایه: CallDto → CallEntity (در RemoteMediator) و CallEntity → Call domain model (در PagingSource map).
  4. شبکه فقط با safeApiCall — نه try/catch در RemoteMediator.
  5. یک Database واحد — جداول calls در :core:database ثبت می‌شوند، نه DB مجزا.
  6. TTL و Refresh policy متمرکز در RemoteMediator.

۸.۸ کپی‌برداری برای featureهای آینده

اگر روزی feature myloads یا cargoSearch نیاز به cache/offline پیدا کرد:

  1. ساختار :feature:calls/data/local/ و paging/ را به feature هدف کپی کن.
  2. Entity, Dao, RemoteKey, RemoteMediator را با مدل feature جدید جایگزین کن.
  3. Entity جدید را در :core:database (AppDatabase.entities و version bump + Migration) ثبت کن.
  4. تمام.

این یعنی هزینه‌ی افزودن Room به featureهای بعدی ≈ ۱ روز کار به‌جای ۱ هفته‌ی طراحی از صفر.

۸.۹ سایر featureها (بدون Room)

flowchart LR
    UI[UI] --> VM[ViewModel]
    VM --> UC[UseCase]
    UC --> Repo[RepositoryImpl]
    Repo -->|"safeApiCall"| Api[Retrofit Api]
  • جریان ساده: UI → ViewModel → UseCase → Repository → safeApiCall → Api.
  • بدون Room، بدون RemoteMediator.
  • در صورت اینترنت قطع: UiState با AppError.Network → نمایش error state در UI.

۸.۱۰ Anti-patterns مختص این بخش

  • ✕ ساخت Database مجزا برای feature calls (همه‌ی Entityها در یک AppDatabase ثبت شوند)
  • ✕ استفاده از Room در featureهای دیگر بدون justify (افزودن پیچیدگی بدون نیاز)
  • ✕ فراخوانی مستقیم Api در ViewModel به‌جای عبور از Pager + RemoteMediator
  • ✕ Bypass کردن safeApiCall در RemoteMediator

۱۷. Testing Strategy — فقط Konsist (تست‌های معماری)

به‌دلیل کمبود وقت، تنها لایه‌ی تست ضروری در فاز اول، Konsist است (تست‌های ساختاری/معماری). تست‌های واحد، یکپارچه، UI، E2E و Performance در فازهای بعد به‌تدریج اضافه خواهند شد و در این پلن خارج از scope هستند.

۱۷.۱ هدف

  • یونیت تست برای معماری: قواعد ساختاری به‌جای README، در CI اجرا می‌شوند.
  • جلوگیری از drift معماری در طول زمان (به‌خصوص در رشد تیم).
  • مرز ماژول‌ها در زمان CI گارد می‌شود.
  • هزینه‌ی نگهداری بسیار پایین (۲–۳ روز نوشتن، عمر طولانی).

۱۷.۲ محل قرارگیری

  • ماژول جداگانه: :konsist-test
    • وابسته به: تمام ماژول‌های :core:*, :shared-kernel, :feature:*.
    • فقط testImplementation("com.lemonappdev:konsist:<version>").
  • اجرا: ./gradlew :konsist-test:test
  • اتصال به CI: gate قبل از merge.

۱۸. Anti-patterns ممنوع

  • ✕ ViewModel که Repository تزریق می‌کند (به جای UseCase)
  • ✕ بیش از یک MutableStateFlow در یک ViewModel برای state صفحه
  • ✕ MutableLiveData (کلاً LiveData حذف)
  • ✕ Composable که Repository یا UseCase تزریق می‌کند (الان در ReportViolationScreen.kt وجود دارد)
  • ✕ Feature که feature دیگر را import می‌کند
  • ✕ ساخت OkHttp/Retrofit/Interceptor بیرون از :core:network
  • ✕ ساخت Room Database بیرون از :core:database
  • ✕ افزودن Room به featureهای جدید بدون پیروی از الگوی پایلوت :feature:calls
  • ✕ فراخوانی مستقیم api.xxx() در Repository بدون عبور از safeApiCall
  • ✕ try/catch روی HttpException یا IOException در Repository (مدیریت متمرکز در safeApiCall)
  • ✕ Parse دستی errorBody در Repository (با ApiErrorParser متمرکز)
  • ✕ کلاس Public بدون نیاز در ماژول feature
  • ✕ فایل > ۶۰۰ خط یا Composable > ۴۰۰ خط
  • ✕ Domain که به android.* وابسته شود
  • ✕ Mixed source set (src/main/java/ + src/main/kotlin/ در یک ماژول)
