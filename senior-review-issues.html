CriticalC2. هیچ safeApiCall وجود ندارد — ۲۱ Repository دستی try/catch می‌کنندC2

گرپ روی safeApiCall در کل پروژه = صفر نتیجه. در عوض ۲۱ فایل Repository هرکدام کد زیر را تکرار کرده‌اند:

try {
    val response = api.xxx()
    if (response.isSuccessful) Result.Ok(...) else Result.Err(...)
} catch (e: HttpException) { ... }
catch (t: Throwable) { Result.Err(mapError(t)) }

مثال‌های بدتر:

  • data/.../auth/AuthRepositoryImpl.kt — ۸ بلاک catch روی Throwable در یک فایل ۴۵۹ خطی.
  • data/.../cargo/CargosRepositoryImpl.kt — ۷ catch روی Throwable.
  • data/.../driver/DriverCargoRepositoryImpl.kt — ۶ catch.
راه‌حل: پیاده‌سازی SafeApiCall.kt در :core:network طبق امضاهای پلن §۷.۴، بعد جایگزینی تدریجی + قاعده‌ی Konsist «Direct api.* call without safeApiCall is forbidden».
HighC3. Parse دستی errorBody در ۱۲ RepositoryC3

هر Repository خودش json.decodeFromString<ProblemDetailsDto>(...) می‌نویسد. دو DTO با نام ProblemDetailsDto در پروژه وجود دارد (یکی در :core:network، یکی در :data).

راه‌حل: یک ApiErrorParser + ProblemDetailsDto RFC-7807 در :core:network، حذف نسخه‌ی data.
HighC4. هم AuthInterceptor و هم TokenAuthenticator توکن را refresh می‌کنندC4

در AuthInterceptor.kt منطق refresh + retry با synchronized نوشته شده. در TokenAuthenticator.kt هم همین منطق دوباره. این دو می‌توانند هم‌زمان trigger شوند → دو refresh موازی، token race، invalidation متقابل.

علاوه بر این، synchronized(refreshLock) داخل OkHttp dispatcher thread یعنی هر درخواست همزمان روی refresh قفل می‌شود (پشت سر هم).

راه‌حل (پلن §۱۴): یک TokenAuthenticator تنها (Single-flight با Mutex از kotlinx-coroutines)، حذف منطق refresh از AuthInterceptor.
HighC5. کد «Trust All Certs» کامنت‌شده در فایل productionC5

در core/network/.../NetworkModule.kt:34-50 یک تابع applyUnsafeTrustManager کامنت ولی روی شاخه‌ی main commit شده است. خطر: یک developer تازه‌وارد uncomment می‌کند و به prod ship می‌شود.

راه‌حل: حذف کامل + اضافه کردن CertificatePinner طبق پلن §۱۴.
HighC6. Cert Pinning وجود نداردC6

پلن §۱۴ صریحاً CertificatePinner را قید کرده. هیچ CertificatePinner در :core:network پیدا نشد.

MediumC7. explicitNulls = false در Json configC7

این flag باعث می‌شود null برای فیلدهای optional سرور نادیده گرفته شود. اگر سرور یک فیلد required جدید اضافه کند و null برگرداند، در client هیچ خطایی نخواهد داد و باگ‌های منطقی ایجاد می‌شود.

راه‌حل: برای DTOهایی که قطعاً nullable هستند، val x: String? = null به‌صراحت تعریف شود؛ explicitNulls پیش‌فرض true بماند.

یک خلاصه‌ی نهایی

پروژه در سطح «MVP که زنده است» قرار دارد، نه «محصول آماده‌ی مقیاس میلیون کاربر». نقاط قوت: ساختار اولیه‌ی modular، استفاده از Hilt، Compose، Coroutines، EncryptedPreferences، Crashlytics. نقاط ضعف اصلی: هیچ‌کدام از قواعد طلایی پلن (UseCase/safeApiCall/internal/God-file/feature-isolation) رعایت نشده‌اند. تمام ۱۲ قاعده‌ی Konsist که پلن §۱۷ پیشنهاد داده، الان در پروژه شکست می‌خورند. خبر خوب: همه‌ی این‌ها mechanical و قابل refactor هستند، مشروط به اینکه تیم بپذیرد اول guard های معماری (build-logic + konsist-test) را برپا کند، بعد مهاجرت تدریجی feature به feature شروع شود.

اگر بخواهید فردا یک تیم ۵-۸ نفره استخدام کنید، بدون این refactor چندین هفته طول می‌کشد تا یک developer جدید بفهمد ListScreen.kt چه کار می‌کند. با refactor (۸-۱۲ هفته) به نقطه‌ای می‌رسید که هر تیم روی feature خودش بدون merge-conflict کار می‌کند.
